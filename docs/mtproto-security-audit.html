Bottom line. Both remote pre-authentication crashes are fixed. They were in MtProtoKit, which still creates and binds every key in the app, also for the Rust engine. So are all four medium findings except AUTH_KEY_DUPLICATED, which was left alone by decision.

Each crash, truncation, clock and -404 fix has a regression test that fails on the old code. The engine's 175 security requirements are now a runnable bench (scripts/security-bench.py), and none of them fail.

In twelve places the engine is stricter than tdlib against input an attacker or a hostile server controls. They are listed below with the tdlib line and our test.

Second pass, same day. Every remaining low finding is now fixed too, apart from the ones listed under "Not fixed, and why":

  • temp-key rotation;
  • the _dc handshake constructors;
  • bind expiry and bind-failure handling;
  • CDN key refresh;
  • the anonymous CDN header;
  • tdlib's padding buckets;
  • no plaintext in logs;
  • zeroization and FFI documentation.
The handshake changes and the rotation were checked live against production and the test servers.

Scope

  • Rust MTProto engine (github.com/TelegramMessenger/mtproto-engine, third-party/mtproto-engine): sessions, transport, obfuscation, MTProxy and SOCKS5, CDN connections. It runs every session in the macOS app.
  • MtProtoKit: in the app it still performs every auth-key exchange and temp-key binding, because the engine runs with generate_key = 0. Telegram iOS uses the same code.
  • Host glue and TelegramCore: MTProtoRustEngine (RustNetworkSession) and the CDN download path (FetchV2, MultipartFetch).

The requirements came from 155 entries in the official docs (quotes verified against the fetched pages) and 178 checks read in tdlib's code (file and line). Each was cross-checked against our code by two independent audits. MtProtoKit's key exchange had a third audit of its own. Crash findings were reproduced before they were fixed.

Fixed in MtProtoKit (key creation and binding)

Why this mattered for the macOS app. The Rust engine gets its keys from MtProtoKit, so MtProtoKit's handshake runs over the user's connection and proxy. An attacker can force a new key exchange at any time with a forged, unauthenticated -404 frame. Key exchanges also happen for every new DC, media or CDN connection, and when a temp key expires.

So the two high findings could be triggered on demand by an on-path attacker or by the operator of a configured proxy. Telegram iOS shares this code and gets the same fixes.

IDSeverityProblemFixTest
H1 / F1High Remote crash. A forged server_DH_params_ok with a 20–35-byte encrypted_answer made the padding-stripping loop throw an uncaught NSRangeException. The attacker needs only the plaintext nonces. The answer is parsed first. The inner length comes from the TL structure, padding must be under 16 bytes (as in tdlib), and SHA1 is checked over exactly that span. The stripping loop is gone. testShortServerDhAnswersAreRejectedWithoutThrowing (on the old code, the real exception), testServerDhAnswerIsParsedBeforeItsPaddingIsChecked
H2 / F2High Remote crash or hang. A pq of 0 or 1 was SIGFPE on Intel. On Apple Silicon Release builds it was an endless loop on the process-wide MtProtoKit queue, which froze all key creation. pq must be 1–8 bytes and between 4 and 263, checked before factorizing. MTFactorize has the same guard itself, handles even numbers directly, has its shift capped, and uses a 64-bit q. testFactorizeRejectsDegenerateValues, testFactorizeSplitsEvenAndOddProducts, testFactorizeGivesUpOnALargePrimeInBoundedTime, testHostilePqIsRejectedBeforeFactorizing, testValidPqIsFactorizedAndUsed. The original repro binaries return at once at -Os on arm64 and x86_64.
M5 / F3Medium A failed handshake was retried at network speed, with the attacker choosing the CPU cost of each round. Unauthenticated frames also reset the TCP backoff. Every failure goes through one path with backoff: an immediate retry, then 1, 2, 4, 8 and 16 s. The count resets on dh_gen_ok. Unauthenticated frames no longer reset the TCP backoff, and key fingerprints are computed once. testRepeatedHandshakeFailuresBackOff, testUnauthorizedConnectionsDoNotTreatIncomingDataAsAuthenticated
F4Low auth_key was not left-padded to 256 bytes, so about 1 in 256 handshakes failed and left the server with an orphan key. The key is left-padded to 256 bytes, and any other length fails the handshake. g_b stays minimal-length on the wire, as tdlib and our engine send it. Covered by the handshake tests
F5Low The client's own g_b was not range-checked. g_b must pass the same bounds as g_a. Up to 8 fresh exponents are tried, then the handshake fails. Covered by the handshake tests
F6Low SecRandomCopyBytes failures were ignored for nonce, new_nonce and b. An RNG failure, or a nil RSA or AES result, fails the handshake. Strict compile; code review
F8Low The initial server salt from the handshake was thrown away and salt 0 was stored, so every new key cost a bad_server_salt round trip. The computed salt is stored with the key. server_time is still not taken from the handshake: MtProtoKit corrects its clock from authenticated messages. Handshake tests
F12Low A single forged -404 during a media bind marked the temp key as bound. That was the 2024 "attempt to fix expired key" workaround. The engine's confirmation rule now applies to main and media binds. One -404 changes nothing. A second one in a row fails the bind, and MTContext retries with a new key and backoff. Any authenticated message in between clears the count. Today's debug and beta logs show media binds getting normal results. testOneUnconfirmedKeyRejectionDoesNotFinishABind, testAConfirmedKeyRejectionFailsTheBindOnce, testAnAuthenticatedMessageClearsAnEarlierKeyRejection
F13Low There was no size check on the CDN RSA modulus, so a short key made the RSA_PAD loop effectively endless. The modulus must be exactly 256 bytes, the key is parsed once, and RSA_PAD stops after 4096 attempts. The "use our only CDN key when no fingerprint matches" fallback is unchanged. Code review
F14Info MTRsaFingerprint used a static scratch buffer, which is not thread-safe. It is now a local buffer. —
F7Low The key exchange used the legacy p_q_inner_data constructors without dc, so the server could not detect a handshake redirected to another DC. It now uses p_q_inner_data_dc / _temp_dc, with tdlib's rule for dc: the DC id, plus 10000 on test servers, made negative on a media-only address (never for a CDN). Verified live: production DC2 with dc 2 (permanent and temporary keys), dc −2 (a media temp key on a media address), and the test DC with 10002. testInnerDataDatacenterIdFollowsTheDocumentation, testInnerDataUsesTheConstructorsWithADatacenter, live bench runs
F9Low Temp keys were never replaced before expiry, so every day a key died mid-use and recovery went through the -404 path. The app replaces each temp key it uses an hour before it expires, as tdlib does. A new key is created and bound while the old one keeps working, then sessions switch to it.
  • A late -404 for the old key adopts the replacement instead of deleting it.
  • Rotation is off in app extensions.
  • It stops for good if the server no longer knows the permanent key.
  • It re-checks every 5 minutes, so it still works after sleep.
Verified live with a 60 s key on production: replaced at 45 s, 150 of 150 requests answered, no -404, no latency spike.		 testATemporaryKeyIsReplacedBeforeItExpires, testOnlyTheAppReplacesTemporaryKeys, testAnExpiredKeyIsLeftToTheRejectionPath, testAConnectionSwitchesToAReplacementKey, testARejectionOfAReplacedKeyKeepsTheReplacement
F10Low The bind's expires_at was "now + 24 h" at bind time, not the key's real expiry. The key's expiry is counted from when its inner data is built, and the bind sends it in server time, as tdlib does. testBindExpiresAtIsTheKeysOwnExpiryInServerTime
F11Low If the permanent key vanished during a temp handshake, the action never ended, which blocked new key requests for that DC. Any bind error also discarded the new temp key. The action now fails, so the context retries with backoff. Transient bind errors (5xx, flood) re-bind the same temp key up to 3 times, as tdlib does, and other errors fail as before. testAnActionWhosePermanentKeyVanishedFails
F13aLow CDN keys were never refreshed, and a fingerprint mismatch went straight to our only cached key. A mismatch now fetches the CDN keys from the main DC again first. See the note in "Not fixed" for the fallback that is kept after that. testACdnFingerprintMismatchFetchesTheCdnKeysOnceThenUsesTheOnlyKey
F15Info A parse error logged up to 128 bytes of decrypted plaintext. It now logs only the length and the body constructor. Code review

The MtProtoKit suite passes 97 of 97 on macOS: 75 existing tests and 22 new, and the new ones fail with their fixes removed. The strict iOS-simulator and macOS 10.13 compile of every source reports 0 warnings.

Fixed in the host and TelegramCore

IDSeverityProblemFixTest
M3Medium A hostile CDN could silently truncate any file it served. An empty reply skipped hash verification and was committed as end-of-file, a short reply on a 128 KiB boundary passed, and the stored size was then lowered. A CDN part must be exactly the requested length, or end exactly at the size the master DC declared, and must never run past that size.
When the size is unknown, a short part is accepted only if it ends inside a 128 KiB hash block, where the master's hash proves it is the real end.
Anything else sends the download back to the master DC with the CDN disabled. A master that keeps sending bad-key redirects after that makes the download fail instead of loop.		 CdnPartValidationTests (4). Hostile-CDN bench row truncated: 2/2 clean with the fix; the old code failed 0/2 with 12 bad-data events.
M4Medium A hostile CDN could set the app-wide clock. Its time difference was written into the shared context, which moved auto-delete timers, outgoing dates and the clock other sessions start from. Only non-CDN sessions update the shared clock. A CDN session keeps its time to itself. testOnlyNonCdnSessionsMoveTheAppClock (fails without the fix), testOnlyNonCdnSessionsShareTheirTimeDifference
B-8Low A CDN redirect IV shorter than 4 bytes caused an out-of-bounds memcpy write. Only a malicious main DC could send one. The redirect key must be 32 bytes and the IV 16, as in tdlib. Otherwise the download falls back to the master DC (FetchV2) or fails cleanly (MultipartFetch). testRedirectKeyMaterialMustBeAes256CtrSized. Bench row bad-redirect-key: 1.00 bytes served per byte needed with the fix, 1.34 and 5 re-uploads on the old code.

Fixed in the Rust engine

All of these are in github.com/TelegramMessenger/mtproto-engine. Each test fails on the code before the fix and passes after it.

IDSeverityProblemFixTest
M1Medium A forged, unauthenticated 4-byte -404 frame made the engine drop the session and re-send in-flight requests in a new session, so a request the server had already executed could run twice. The host then removed the temp key, so every session sharing it paused, re-keyed and replayed as well. A -404 now only closes the connection. The session, its requests and the key are kept. The key is reported invalid only when a fresh connection is rejected again before any valid packet arrives. A real expired key is still replaced within about a second. a_forged_404_keeps_the_session_and_executes_once (cold and warm connection), unknown_key_reports_invalid_and_recovers_with_new_key
A-L1/L3Low A replayed packet older than the duplicate window could set the session clock, and so could a withheld answer to a request sent long ago, which counted as a "freshness proof". Replay-mode packets never touch the clock and are dropped outside the time window. A freshness proof must answer a message we sent within the last 300 s of local monotonic time, not of the server clock, which a glitch or an attacker could have moved. So neither a withheld answer nor a withheld pong works. replays_below_the_window_never_move_the_clock, a_withheld_answer_cannot_drag_the_clock_back, a_withheld_pong_cannot_drag_the_clock_back
A-L4Low A fake 16 MiB frame trickled at about 512 B/s could stall a session for around 9 hours. Mitigated. Inbound frames are capped at 4 MiB + 1 KiB (tdlib's limit), checked from the length header before anything is buffered. With the existing 512 B/s progress floor, a trickled fake frame now holds a session for at most about 2.3 h. A stricter per-frame deadline was tried and dropped in review, because it would cut real slow links (several media sessions sharing a 2G or tethered link). inbound_frames_above_four_mib_are_rejected_from_the_header, trickling_or_noisy_connections_are_abandoned_and_requests_complete (modes 0–3), slow_link_trickling_bytes_never_times_out
B-6Low A CDN answering AUTH_KEY_PERM_EMPTY forever parked the download forever. A CDN session surfaces the error after one retry, so the download falls back to the master DC. cdn_auth_key_perm_empty_surfaces_after_one_retry
HygieneInfo Proxy secrets and session verification tokens could be printed by Debug. Derived obfuscation keys and the raw proxy secret stayed in memory after use. Manual redacting Debug for DcAddress and Verification. Derived obfuscation keys are zeroized after the ciphers are built, ProxySecret zeroizes on drop, and the decoded link temporary is wiped. The secret copies in DcAddress and ProxyConfig are not yet wiped. debug_output_redacts_proxy_secrets_and_verification_tokens
B-5Low CDN DCs, which third parties run, received the full initConnection: device model, OS version, language pack and the MTProxy address. CDN sessions now send tdlib's anonymous header: n/a for device and system, no language pack, no proxy, no parameters. The docs require this. cdn_sessions_send_an_anonymous_init_connection
A-L5Low Padding on direct connections was 0–64 random bytes, so message sizes leaked to within 64 bytes. Direct connections pad to tdlib's size buckets (64…1280 bytes, then 448-byte steps). Proxied connections keep 0–240 random bytes. bucketed_padding_hides_sizes_like_tdlib
Hygiene 2Info Some secret copies were not wiped. FFI ownership rules were undocumented. The fuzzer never reached RSA parsing. An RSA key with exponent 1 was accepted. These are now wiped:
  • the proxy secrets in DcAddress / ProxyConfig and the SOCKS5 password;
  • the handshake's new_nonce (best effort), also when RSA fails;
  • secret FFI payloads dropped after shutdown.
The FFI ownership and lifetime rules are documented (docs/swift-integration.md §15). A new rsa fuzz target covers PEM and DER, and RSA keys must have an odd exponent of at least 3.		 public_exponent_must_be_odd_and_at_least_three, fuzz target rsa

Where our implementation is stronger than tdlib

Every row was checked in both codebases: tdlib at e894536b2f (file and line in the tdlib column), and our engine through the named tests. These are places where tdlib accepts input that an attacker or a hostile server controls, and the engine does not. In the macOS app the engine runs every session, while key creation still goes through MtProtoKit (next section).

ChecktdlibOur engineWho could exploit tdlib's behaviourEvidence
A forged -404 On -404 a PFS session drops its temp key at once, and a CDN session drops the CDN key and fails the session (Session.cpp:619-662). The frame is 4 unauthenticated bytes. One -404 only reconnects. The key is dropped only after a fresh connection is also rejected before any valid packet. Requests are never re-executed. Anyone on the path, or a proxy operator: forced re-keying on demand. a_forged_404_keeps_the_session_and_executes_once
Inbound frame size The 4 MiB cap is checked only while a frame is incomplete. A frame that arrives whole in one read is accepted at any size (RawConnection.cpp:158-173). The cap is checked from the length header before anything is buffered. Anyone on the path: memory and stall DoS before any MAC check. inbound_frames_above_four_mib_are_rejected_from_the_header, trickling_or_noisy_connections_are_abandoned_and_requests_complete
gzip bombs No limit on decompressed size, and gzip inside gzip is allowed (Gzip.cpp:157-185, SessionConnection.cpp:408-412). Each gzip_packed is capped at 32 MiB, and a packet shares one unpacking budget. A declared size over the limit is refused before inflating. A hostile or compromised server: memory exhaustion. gzip_bombs_are_refused_without_unpacking_them; fuzzer TL and session generators
Containers Nested containers are allowed with no depth limit, the 1024-message count is not enforced, and trailing bytes are ignored (SessionConnection.cpp:214-231). At most 1024 messages per container and 4096 per packet, with nesting depth capped at 8. A hostile server: stack exhaustion. container_parse_and_limits, container_parser_never_panics_on_any_layout; test-server fault "deep nesting"
bad_msg_notification / bad_server_salt Applied without checking that bad_msg_id is a message the client sent (SessionConnection.cpp:324-397). Acted on only for msg_ids the client actually sent, and ignored when replayed. A hostile server or a replay: forced resends, salt changes, clock moves. notifications_about_messages_we_never_sent_are_ignored, replayed_old_salt_and_bad_msg_notifications_are_ignored
future_salts req_msg_id is not checked; salt ranges are taken verbatim (SessionConnection.cpp:435-449). Accepted only as the answer to one of our last requests. Non-finite or inverted ranges are dropped. A hostile server or a replay: salt poisoning. future_salts_must_answer_our_request
new_session_created unique_id is not deduplicated, so a repeated notice re-triggers resends and getDifference (Session.cpp:701-732). unique_id is deduplicated, and the notice is ignored in replay mode. A replay: amplification. duplicate_new_session_notifications_are_ignored
Replayed old packets A packet below the 1000-id window fails the whole session: new session_id, every query re-sent (SessionConnection.cpp:727-739). It is acked and handled idempotently, and it can never move the clock. A freshness proof must answer a message sent within the last 300 s of local time. A replay inside the 300 s window: session resets on demand. too_old_messages_are_acked_and_replayed_safely, replays_below_the_window_never_move_the_clock, a_withheld_answer_cannot_drag_the_clock_back, a_withheld_pong_cannot_drag_the_clock_back
Fake-TLS ServerHello The HMAC is compared with !=, not in constant time (TlsInit.cpp:535-539). Compared in constant time (Mac::verify_slice). An active prober: a timing side channel on the proxy secret check. server_hello_roundtrip (mismatch case), mtproxy_fake_tls_secret
pq in the handshake No size bound. Large values go to a bignum Pollard-rho of up to ~5.9·107 iterations before the size check, and a prime pq yields p = 1, which is accepted (crypto.cpp:103-140,171-255). 1–8 bytes, ≥ 4, composite, with a fixed work budget. Anyone on the path (resPQ is unauthenticated): CPU burn per handshake. hostile_pq_values_fail_fast_without_hanging, primes_and_hostile_values_are_rejected_quickly
dh_gen_retry / dh_gen_fail Acted on without checking nonces or new_nonce_hash2/3 (Handshake.cpp:277-280). All three answers are verified in constant time before acting. Anyone on the path: aborting key creation with a forged answer. dh_gen_hash_mismatch_is_rejected
Process aborts Some server-controlled values reach CHECK and abort the process: an out-of-range CDN redirect DC id, and *_MIGRATE_X on the non-main path (DcId.h:20-38). No panic is reachable from network input. The fuzzer runs with overflow checks on, and the test server injects hostile faults. A hostile server: a crash. decrypt_never_panics, handshake_never_panics_on_garbage, hostile_server_faults_never_break_exactly_once_delivery

Parity, not "better": the core crypto (msg_key in both directions, KDF2, AES-IGE, constant-time msg_key compare, length and padding bounds), the RSA key pinning, and the DH prime and generator checks match tdlib exactly.

What holds up

  • Core crypto: msg_key in both directions over the decrypted text including padding, KDF2 and AES-IGE. Length and padding bounds. The same reaction to every pre-MAC error, constant-time compares, MTProto 2.0 only on input, and no panic reachable without the key.
  • Service messages: responses cannot reach the wrong query, CDN answers cannot complete other DCs' queries, and updates from CDN sessions are dropped.
  • MtProtoKit key exchange: the trusted RSA keys are byte-identical to tdlib's and an unknown fingerprint is never accepted. RSA_PAD, every nonce check, the DH prime, g and g_a checks, and new_nonce_hash1/2/3 are correct. The key handoff to Rust is wiped on both sides.
